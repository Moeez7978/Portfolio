11:T798b,<h1><img src="https://icon.icepanel.io/AWS/svg/Networking-Content-Delivery/Elastic-Load-Balancing.svg" width="40" align="center"/> Amazon ELB — Complete Guide for AWS Solutions Architect Associate</h1>
<h3>Part 1 of 3 — Architecture, Types &#x26; Core Concepts</h3>
<blockquote>
<p><strong>Elastic Load Balancing (ELB)</strong> is AWS's managed load balancing service that automatically distributes incoming application traffic across multiple targets — EC2 instances, containers, IP addresses, and Lambda functions — across one or more Availability Zones.</p>
</blockquote>
<hr>
<h2>📐 Why Load Balancing Exists — The Problem It Solves</h2>
<p>Before ELB, scaling an application meant manually managing traffic distribution. A single server handling all requests is a <strong>Single Point of Failure (SPOF)</strong>. Load balancers solve three fundamental problems:</p>
<pre><code>Without LB:                          With LB:
                                      
  User ──────► Server A              User ──────► Load Balancer ──► Server A
               (overloaded,                                      ──► Server B
                crashes)                                         ──► Server C
</code></pre>
<table>
<thead>
<tr>
<th>Problem</th>
<th>Without ELB</th>
<th>With ELB</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Single Point of Failure</strong></td>
<td>One server down = app down</td>
<td>Traffic rerouted to healthy targets</td>
</tr>
<tr>
<td><strong>Scaling</strong></td>
<td>Manual, slow</td>
<td>Automatic distribution across new instances</td>
</tr>
<tr>
<td><strong>Health</strong></td>
<td>No automatic detection</td>
<td>Continuous health checks, unhealthy targets removed</td>
</tr>
<tr>
<td><strong>SSL Termination</strong></td>
<td>Each server manages certs</td>
<td>Centralized at the LB</td>
</tr>
<tr>
<td><strong>Sticky Sessions</strong></td>
<td>Complex to implement</td>
<td>Built-in cookie-based stickiness</td>
</tr>
</tbody>
</table>

<h3>Core Infrastructure Components</h3>
<table>
<thead>
<tr>
<th>Component</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Load Balancer Node</strong></td>
<td>Physical/virtual node deployed per AZ. Receives traffic and distributes it.</td>
</tr>
<tr>
<td><strong>Listener</strong></td>
<td>Process that checks for connection requests on a protocol/port (e.g., HTTPS:443).</td>
</tr>
<tr>

<td>Logical grouping of targets (EC2, Lambda, IPs) that receive traffic.</td>
</tr>

<td>Individual resource receiving traffic (EC2 instance, container, IP, Lambda).</td>
</tr>

</tr>

<h3>ELB Node Placement</h3>
<p>When you create an ELB and enable it for multiple AZs, AWS deploys <strong>one ELB node per AZ</strong>. Each node gets its own IP address. The ELB DNS name resolves to all active node IPs.</p>
<pre><code>                    ┌─────────────────────────────────────────┐
                    │           AWS Region (us-east-1)         │
                    │                                          │
  Internet ──DNS──► │  ELB DNS: my-alb-123.us-east-1.elb.amazonaws.com
                    │         │              │                 │
                    │    ┌────▼────┐    ┌────▼────┐           │
                    │    │  Node   │    │  Node   │           │
                    │    │  AZ-1a  │    │  AZ-1b  │           │
                    │    └────┬────┘    └────┬────┘           │
                    │         │              │                 │
                    │    ┌────▼────┐    ┌────▼────┐           │
                    │    │ Targets │    │ Targets │           │
                    │    │  AZ-1a  │    │  AZ-1b  │           │
                    │    └─────────┘    └─────────┘           │
                    └─────────────────────────────────────────┘
</code></pre>
<hr>
<h2>🌐 DNS → Load Balancer → Resources Flow</h2>
<p>This is the complete request journey from a user's browser to your backend resources:</p>
<pre><code>┌─────────────────────────────────────────────────────────────────────────────┐
│                     COMPLETE REQUEST FLOW                                    │
│                                                                              │
│  1. USER TYPES URL                                                           │
│     Browser: https://app.example.com                                         │
│                          │                                                   │
│                          ▼                                                   │
│  2. DNS RESOLUTION (Route 53)                                                │
│     Route 53 Hosted Zone: example.com                                        │
│     ALIAS Record: app.example.com → my-alb-123.us-east-1.elb.amazonaws.com  │
│     Returns: IP of nearest ELB Node (e.g., 54.12.34.56)                     │
│                          │                                                   │
│                          ▼                                                   │
│  3. TCP CONNECTION TO ELB NODE                                               │
│     Client connects to ELB Node IP on port 443                               │
│     TLS Handshake happens HERE (SSL Termination at LB)                       │
│                          │                                                   │
│                          ▼                                                   │
│  4. LISTENER EVALUATION                                                      │
│     Listener: HTTPS:443                                                      │
│     Rules evaluated top-to-bottom:                                           │
│       Rule 1: IF path = /api/*  → Forward to TargetGroup-API                │
│       Rule 2: IF path = /admin/* → Forward to TargetGroup-Admin             │
│       Default: Forward to TargetGroup-Web                                    │
│                          │                                                   │
│                          ▼                                                   │
│  5. TARGET GROUP SELECTION                                                   │
│     Target Group: TargetGroup-Web                                            │
│     Algorithm: Round Robin / Least Outstanding Requests                      │
│     Health Check: Only healthy targets eligible                              │
│                          │                                                   │
│                          ▼                                                   │
│  6. REQUEST FORWARDED TO TARGET                                              │
│     EC2 Instance / Container / Lambda / IP                                   │
│     New TCP connection opened from ELB Node → Target                        │
│     (Client IP preserved via X-Forwarded-For header)                        │
│                          │                                                   │
│                          ▼                                                   │
│  7. RESPONSE RETURNS                                                         │
│     Target → ELB Node → Client                                               │
└─────────────────────────────────────────────────────────────────────────────┘
</code></pre>
<blockquote>
<p>💡 <strong>Key Insight:</strong> The client never talks directly to your backend. The ELB node terminates the client connection and opens a <strong>new, separate connection</strong> to the target. This is called a <strong>two-connection model</strong>.</p>
</blockquote>

<h2>1️⃣ Classic Load Balancer (CLB) — Legacy</h2>
<blockquote>
<p><strong>Verdict: Do NOT use for new applications. AWS recommends migrating to ALB or NLB.</strong></p>
</blockquote>
<p>The original ELB. It operates at both Layer 4 and Layer 7 but with very limited Layer 7 capabilities. It only supports <strong>one SSL certificate</strong> and <strong>one application per CLB</strong>.</p>
<h3>Why It's Legacy</h3>
<pre><code>CLB Limitations:
  ✗ One SSL cert per CLB (expensive for multi-domain apps)
  ✗ No content-based routing (no path/host rules)
  ✗ Only supports EC2-Classic and EC2-VPC (old instances)
  ✗ No support for containers, Lambda, or IP targets
  ✗ No WebSocket support
  ✗ No SNI (Server Name Indication)
</code></pre>
<h3>When You Still See It</h3>
<ul>
<li>Legacy applications built before 2016</li>
<li>Exam questions testing your knowledge of its limitations</li>
<li>Migration scenarios (CLB → ALB/NLB)</li>
</ul>
<hr>
<h2>2️⃣ Application Load Balancer (ALB) — Layer 7</h2>
<p>The <strong>most feature-rich</strong> ELB type. Operates at Layer 7 (HTTP/HTTPS) and understands the content of requests — headers, paths, query strings, methods, and source IPs.</p>
<h3>ALB Architecture</h3>
<pre><code>                         ┌──────────────────────────────────────┐
                         │        Application Load Balancer      │
                         │                                       │
  HTTPS:443 ──────────►  │  Listener: HTTPS:443                 │
                         │  Certificate: ACM cert (SNI support)  │
                         │                                       │
                         │  Rules (evaluated top → bottom):      │
                         │  ┌─────────────────────────────────┐  │
                         │  │ IF host = api.example.com       │  │
                         │  │ AND path = /v2/*                │  │
                         │  │ → Forward → TG-API-v2           │  │
                         │  ├─────────────────────────────────┤  │
                         │  │ IF path = /images/*             │  │
                         │  │ → Forward → TG-Images           │  │
                         │  ├─────────────────────────────────┤  │
                         │  │ IF method = POST                │  │
                         │  │ → Forward → TG-Writers          │  │
                         │  ├─────────────────────────────────┤  │
                         │  │ DEFAULT → Forward → TG-Web      │  │
                         │  └─────────────────────────────────┘  │
                         └──────────────────────────────────────┘
                                  │         │         │
                             ┌────▼──┐ ┌────▼──┐ ┌───▼───┐
                             │TG-API │ │TG-Img │ │TG-Web │
                             │v2     │ │       │ │       │
                             └───────┘ └───────┘ └───────┘
</code></pre>

<h3>ALB — Client IP Preservation</h3>
<p>ALB terminates the client connection. The backend sees the <strong>ELB node's IP</strong>, not the client's IP. To get the real client IP:</p>
<pre><code>X-Forwarded-For: &#x3C;client-ip>, &#x3C;proxy-ip>
X-Forwarded-Port: 443
X-Forwarded-Proto: https
</code></pre>
<blockquote>
<p>💡 <strong>Exam Tip:</strong> ALB is the answer for: content-based routing, microservices, containers (ECS/EKS), Lambda targets, WebSocket, gRPC, Cognito authentication, and WAF integration.</p>
</blockquote>
<hr>
<h2>3️⃣ Network Load Balancer (NLB) — Layer 4</h2>
<p>Operates at <strong>Layer 4 (TCP/UDP/TLS)</strong>. Does NOT inspect HTTP content. Designed for <strong>extreme performance</strong> — millions of requests per second with single-digit millisecond latency.</p>
<h3>NLB Architecture</h3>
<pre><code>                    ┌──────────────────────────────────────┐
                    │        Network Load Balancer          │
                    │                                       │
  TCP:443 ────────► │  Listener: TCP:443                   │
                    │                                       │
                    │  No rules — pure protocol routing     │
                    │  Passes through raw TCP/UDP packets   │
                    │                                       │
                    │  Static IP per AZ (Elastic IP)        │
                    └──────────────────────────────────────┘
                              │           │
                    ┌─────────▼──┐  ┌─────▼──────┐
                    │  Target    │  │  Target    │
                    │  Group     │  │  Group     │
                    │  TCP:443   │  │  UDP:53    │
                    └────────────┘  └────────────┘
</code></pre>

<tr>
<th>Feature</th>
<th>Detail</th>

<h3>NLB Target Types</h3>
<pre><code>Target Group Types:
  ├── instance   → EC2 instance ID
  ├── ip         → Any IP (on-prem, containers)
  └── alb        → Application Load Balancer (NLB → ALB chaining)
</code></pre>
<h3>NLB — TLS Pass-Through vs TLS Termination</h3>
<pre><code>TLS Termination at NLB:
  Client ──TLS──► NLB (decrypts) ──TCP──► Target
  (NLB holds the cert, backend gets plain traffic)

TLS Pass-Through:
  Client ──TLS──► NLB (passes raw TCP) ──TLS──► Target
  (End-to-end encryption, target holds the cert)
  Use when: compliance requires E2E encryption, mutual TLS (mTLS)
</code></pre>
<blockquote>
<p>💡 <strong>Exam Tip:</strong> NLB is the answer for: static IP requirements, UDP traffic, extreme performance (gaming, IoT, financial trading), PrivateLink, and when the backend needs to see the real client IP natively.</p>
</blockquote>

<h2>🔊 Listeners &#x26; Rules — Deep Dive</h2>
<p align="center">
  <img src="https://raw.githubusercontent.com/acantril/aws-sa-associate-saac03/main/1500-HA_and_SCALING/00_LEARNINGAIDS/ELBListners.png" width="750"/>
</p>
<h3>Listener Configuration</h3>
<p>A <strong>Listener</strong> is the entry point of your load balancer. It defines:</p>
<ul>
<li><strong>Protocol</strong> — HTTP, HTTPS, TCP, UDP, TLS, TCP_UDP</li>
<li><strong>Port</strong> — 1–65535</li>
<li><strong>Default Action</strong> — what to do if no rule matches</li>
</ul>
<pre><code>ALB Listener Example:
  Protocol: HTTPS
  Port: 443
  SSL Certificate: arn:aws:acm:us-east-1:123:certificate/abc
  Default Action: Forward to TG-Default

  Rules:
    Priority 1: IF path-pattern = /api/* → Forward to TG-API (weight: 80%)
                                         → Forward to TG-API-v2 (weight: 20%)
    Priority 2: IF host-header = admin.example.com → Authenticate (Cognito)
                                                    → Forward to TG-Admin
    Priority 3: IF http-header X-Beta = true → Forward to TG-Beta
    Default:    Forward to TG-Default
</code></pre>
<h3>Rule Priority</h3>
<ul>
<li>Rules are evaluated <strong>top to bottom</strong> by priority number (1 = highest)</li>
<li><strong>Default rule</strong> always has the lowest priority (evaluated last)</li>
<li>First matching rule wins — subsequent rules are NOT evaluated</li>
</ul>
<h3>Weighted Target Groups (ALB)</h3>
<p>Forward action can split traffic across multiple target groups with weights:</p>
<pre><code>Rule: Forward to:
  ├── TG-Production  (weight: 90)  → 90% of traffic
  └── TG-Canary      (weight: 10)  → 10% of traffic

Use case: Canary deployments, A/B testing, blue/green deployments
</code></pre>
